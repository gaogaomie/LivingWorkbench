# 发布与灾备运行手册

## 1. 发布基线

- 当前应用版本：`0.1.0`。
- 正式发布必须对应一个不可变 Git tag，建议格式为 `v0.1.0`。
- `CHANGELOG.md`、根目录及三个工作区 `package.json` 的版本必须一致。
- 不允许从包含未提交改动的工作区直接发布；先由负责人审核、提交并创建 tag。
- 本手册不会自动提交、打 tag 或推送代码，这些动作需要负责人明确执行。

## 2. 运行环境

- Bun：`1.3.6`，以根目录 `packageManager` 为准。
- Node.js：用于运行服务端生产构建，并需兼容 `better-sqlite3`、`argon2`、`sharp` 的原生模块。
- 持久化目录：SQLite 数据库、恢复前快照目录、上传目录必须位于持久磁盘，不能放在临时容器层。
- 网络：Web 与 Server 建议同域部署；反向代理把 `/api/v1` 转发到 Server。

生产环境至少配置：

```env
NODE_ENV=production
HOST=127.0.0.1
PORT=8787
APP_ORIGIN=https://你的域名
DATABASE_PATH=/持久磁盘/data/daily-life.sqlite
BACKUP_DIRECTORY=/持久磁盘/data/backups
UPLOAD_DIR=/持久磁盘/uploads
SESSION_SECRET=至少32位的随机密钥
SESSION_TTL_DAYS=30
DEEPSEEK_API_KEY=服务端DeepSeek密钥
DEEPSEEK_MODEL=deepseek-v4-pro
```

`DEEPSEEK_API_KEY`、`SESSION_SECRET` 不得写入 Git、前端变量、日志、备份说明或交接文档。DeepSeek 未配置或暂时不可用时，生活解读会明确降级为本地规则；这不会影响核心记录功能。

## 3. 发布前门禁

在仓库根目录执行：

```bash
bun install --frozen-lockfile
bun run check
bun run test:e2e
bun run scripts/check-release-artifacts.ts
```

只有全部通过才允许发布。还需人工确认：

- 当前提交对应的 GitHub `Dependency Security` 工作流已通过；不得把扫描器连接失败、数据库下载失败或超时解释为“零漏洞”。
- `git status` 为空，当前提交已经过审核。
- `CHANGELOG.md` 已把本次内容从 `Unreleased` 移入目标版本。
- 数据库、恢复前快照、上传目录和密钥均有可恢复备份。
- 测试环境已完成迁移、登录、创建记录、删除恢复、备份预检和 AI 降级冒烟验证。

## 4. 首次部署

1. 检出已审核的版本 tag，安装锁定依赖。
2. 准备持久化目录和仅服务账号可读的 `.env`。
3. 执行 `bun run check`，生成 Web 与 Server 生产构建。
4. 执行 `bun run --cwd apps/server db:migrate`。迁移会执行 SQLite `quick_check`，失败时不得启动服务。
5. 使用 `bun run --cwd apps/server start` 启动 Server；用静态服务器托管 `apps/web/dist`。
6. 验证 `/api/v1/health/live` 与 `/api/v1/health/ready` 均返回成功，再开放流量。
7. 初始化管理员仅在首次部署执行；已有生产库禁止重复初始化。

Server 构建产物必须包含：

- `apps/server/dist/server.js`
- `apps/server/dist/migrations/*.sql`
- `apps/server/dist/migrations/meta/*`

Web 构建产物必须包含 `apps/web/dist/index.html`。CI 会检查这些文件，缺少迁移文件的 Server 构建不可发布。

## 5. 升级流程

1. 在旧版本仍运行时导出业务 Excel，作为用户可读备份；它不包含封面、密钥和 Session，不能代替灾备快照。
2. 停止写流量并正常关闭 Server，确保 SQLite 连接和 WAL 已关闭。
3. 冷备份数据库文件、`BACKUP_DIRECTORY`、`UPLOAD_DIR` 和加密保管的环境配置，记录备份时间与旧版本 tag。
4. 检出新 tag，安装锁定依赖并通过发布前门禁。
5. 执行数据库迁移，再启动新版本。
6. 检查健康接口，并完成登录、写入一条测试记录、读取封面和 AI 降级/调用状态验证。
7. 观察错误率和数据库写入；确认稳定后恢复正常流量。

## 6. 回滚流程

本项目不提供向下迁移。若新版本只改应用代码且没有执行新迁移，可以停止新版本并切回旧 tag；一旦执行了数据库迁移，必须使用升级前冷快照回滚：

1. 立即停止写流量并关闭新版本 Server。
2. 保留故障现场副本，禁止直接覆盖唯一数据文件。
3. 恢复升级前的 SQLite 数据库、上传目录和备份目录。
4. 检出旧版本 tag，安装对应锁文件并重新构建。
5. 启动旧版本，检查 live/ready、登录、最近记录、封面和导出功能。
6. 确认数据时间点和影响范围后再恢复流量，并在 `CHANGELOG.md` 或事故记录中说明回滚原因。

不要用 Excel 整体恢复替代完整回滚：Excel 不含书影音封面，也不恢复密钥、Session 和基础设施状态。

## 7. 灾备与恢复演练

- 每日：备份 SQLite、恢复前快照目录和上传目录；密钥配置单独加密保管。
- 每周：在隔离环境恢复最近一次备份，执行 SQLite `quick_check`，验证登录、记录读取和封面文件。
- 每次发布前：额外创建冷快照，至少保留到新版本稳定一个发布周期。
- 每月：完成一次从零环境恢复演练，记录恢复点目标、恢复耗时和缺失文件。

恢复顺序：环境配置 → SQLite 数据库 → 上传目录 → 恢复前快照目录 → 对应版本应用。恢复完成后先隔离验证，再开放流量。

## 8. 发布失败判定

出现以下任一情况必须停止发布或回滚：

- 数据库迁移或 `quick_check` 失败。
- ready 健康检查返回非 2xx。
- 登录、记录写入、删除恢复或备份预检失败。
- 静态资源或 Server 迁移文件缺失。
- 新版本导致数据不可读、封面大面积丢失或持续 5xx。

## 9. 依赖漏洞扫描

- Dependabot 每周检查可升级依赖；`Dependency Security` 在依赖变更、主分支更新、版本 tag、手动触发及每周定时任务中扫描完整 `bun.lock`。
- 扫描器固定为 OSV-Scanner `v2.5.0` 的 Linux AMD64 镜像摘要。它只下载公开 OSV 漏洞数据库，并在 Runner 内离线匹配锁文件，不向查询接口上传项目依赖清单。
- 扫描发现未豁免漏洞或执行异常都会以非零状态阻止通过。结果中的“可修复版本”仍需结合上游兼容性和完整测试评估，禁止无验证地强制覆盖传递依赖。
- `osv-scanner.toml` 只允许记录有明确调用路径分析、负责人复核理由和到期日的临时例外；到期例外会重新使扫描失败，不得无限期续期。
- 当前两项临时例外均截至 `2026-12-02`：Drizzle 开发工具携带的旧 esbuild 未运行受影响的 `serve` API；ExcelJS 调用 UUID v4，而对应公告仅影响带外部缓冲区的 v3/v5/v6。任一上游提供兼容升级后应立即移除例外并更新锁文件。
