# React 前端编码规范

本文是 `apps/web` 的默认开发、审查和自动化修改规范。新增代码必须遵守；修改旧代码时，应在当前改动范围内逐步收敛。服务端代码遵循 [`Fastify 后端编码规范`](./Fastify后端编码规范.md)，代码代理和大模型同时受根目录 [`AGENTS.md`](../AGENTS.md) 约束。

当前前端技术栈为 React 19、TypeScript、Vite、React Router、TanStack Query、Zustand、Axios、Zod、Tailwind CSS、animal-island-ui、Vitest、Testing Library 和 Playwright。本规范以仓库实际技术栈和目录为准，不引入并存的第二套方案。

## 1. 基本原则

- 代码优先服务于阅读者：名称表达意图，组件和函数只承担一个清晰职责。
- 页面负责组合，Hook 负责状态编排，Service 负责业务请求，HTTP Client 负责传输细节。
- 服务端状态、URL 状态、跨页面客户端状态和组件本地状态必须分开管理。
- 优先使用平台语义、现有组件和现有工具；不为“可能复用”提前抽象。
- 每次改动只解决当前问题，不夹带无关重构、依赖升级或全仓库格式化。
- 不得通过 `any`、非空断言、类型强转、禁用规则或删除测试绕过问题。

## 2. 目录与依赖方向

```text
apps/web/src/
├── components/       # 跨页面复用的通用组件
├── config/           # 浏览器环境配置及其校验
├── constants/        # 稳定、跨模块共享的常量
├── contexts/         # 应用级 Provider 组合
├── data-provider/    # TanStack Query Hook、Mutation 与 Query Key
├── layouts/          # 页面框架和导航布局
├── pages/            # 路由页面及页面私有实现
├── router/           # 路由表和路由守卫
├── services/         # HTTP Client、业务 Service、浏览器能力适配
├── stores/           # 跨页面共享的纯客户端状态
├── styles/           # 全局样式、设计 Token 和 Tailwind 入口
└── test/             # 前端测试公共配置
```

依赖方向必须保持单向：

```text
router / pages / layouts / components
                 ↓
          data-provider
                 ↓
             services
                 ↓
      http-client / shared contracts
```

- 页面之间不得相互导入；共享能力应下沉到有明确职责的模块。
- `services` 不得依赖 React、页面、组件、Store 或 Query Hook。
- `data-provider` 可以依赖 Service，但 Service 不得反向依赖 `data-provider`。
- 公共组件不得读取具体业务 Store、调用业务接口或依赖页面内部实现。
- 页面私有组件、Hook 和纯函数放在对应页面目录内；至少被两个独立页面稳定复用后，才评估提升到全局目录。
- `packages/shared` 只提供前后端共享的 Schema、DTO 和契约；不得包含 React、DOM 或浏览器实现。
- 禁止循环依赖和跨层深层导入。需要路径别名时，必须同步配置 TypeScript、Vite 和测试环境。

## 3. React 组件

### 3.1 组件职责

- 使用函数组件。组件应是 Props 和状态到 UI 的可预测映射，渲染期间不得修改外部状态。
- 页面组件负责读取路由信息、调用页面级 Hook、组合区块，并呈现加载、空数据、错误和成功状态。
- 可复用组件通过 Props 接收数据和事件，不隐藏业务请求或全局副作用。
- 不在组件函数内部声明子组件；这会导致组件类型在每次渲染时变化。
- 能直接计算的值在渲染阶段派生，不为派生值额外维护 State 或 Effect。
- 多个字段总是一起变化且更新规则复杂时，使用 `useReducer` 或提取专用 Hook，避免分散的布尔 State。
- 单个组件出现多项职责、难以命名的逻辑或深层嵌套时，按职责拆分；不得只为缩短文件机械拆分。

### 3.2 Props 与事件

- Props 类型放在组件附近，命名为 `<ComponentName>Props`；只在跨文件复用时导出。
- 使用参数解构和明确默认值。可选 Props 必须有清晰的缺省语义，不以 `null`、`undefined` 和空字符串表达同一状态。
- 外部回调使用 `onXxx`，组件内部处理函数使用 `handleXxx`，布尔值使用 `is`、`has`、`can`、`should` 前缀。
- 不用布尔 Props 同时控制多个职责。差异较大时拆为不同组件，或使用语义明确的联合类型。
- 列表使用稳定业务 ID 作为 `key`；只有永不增删、排序和过滤的静态列表才可使用下标。

### 3.3 Hook

- Hook 必须以 `use` 开头，并在组件或其他 Hook 顶层调用；不得放入条件、循环和事件函数。
- 自定义 Hook 封装可复用的状态与副作用，不返回与职责无关的“万能对象”。
- `useEffect` 只用于同步 React 之外的系统，例如 DOM API、事件订阅、定时器或第三方实例。
- 用户操作放在事件处理函数中，接口数据交给 TanStack Query，派生数据直接计算。
- Effect 必须完整声明依赖并清理订阅、定时器和监听器；不得用忽略依赖规则掩盖闭包问题。
- 仅在有可验证的重复计算或渲染成本时使用 `useMemo`、`useCallback` 和 `memo`，禁止机械添加。
- 在 React `StrictMode` 下，初始化和 Effect 必须可安全重复执行。

## 4. 路由与页面

- 所有路由集中在 `router/` 定义，路径常量集中维护；业务组件不得散落硬编码跳转地址。
- 受保护页面统一经过 `AuthGuard`，不得在每个页面重复鉴权和重定向逻辑。
- 路由级页面默认懒加载。供 React Router `lazy` 使用的页面模块导出 `Component`；直接导入的页面使用清晰的具名组件名。
- 页面必须提供可感知的懒加载或水合占位，并由路由级 `errorElement` 兜底未捕获错误。
- 页面入口只做页面级编排。复杂表单、列表项、统计区块和业务 Hook 应留在页面目录内拆分。
- 筛选、排序、分页、当前 Tab 等需要分享链接或刷新保留的状态优先写入 URL。
- 导航使用 React Router API，不直接修改 `window.location`；外部跳转或文件下载除外。

## 5. 服务端状态与数据请求

### 5.1 分层职责

- 页面和组件不得直接调用 Axios、`fetch` 或拼接 API URL。
- `services/http-client.ts` 统一维护基础地址、Cookie、公共请求头、响应解包和错误转换。
- 每个业务 Service 只描述业务操作和 DTO，不处理 Toast、路由跳转、React State 或缓存失效。
- TanStack Query Hook 集中在 `data-provider`，负责 Query Key、缓存策略、启用条件、Mutation 和精确失效。
- API DTO 和校验 Schema 优先从 `@daily-life/shared` 引入，不在前端重复声明等价类型。

### 5.2 API 契约

API 响应统一为：

```ts
interface ApiResponse<T> {
  code: number | string;
  message: string;
  data: T | null;
}
```

- HTTP Client 必须在边界验证并解包 `data`，业务层不得依赖 Axios Response 或原始响应壳。
- 边界输入视为 `unknown`，通过共享 Zod Schema 或明确类型守卫后才能进入 UI。
- 失败统一转换为 `ApiClientError` 等稳定错误类型；用户界面不得解析 Axios 内部结构。
- 请求默认携带 Cookie；写操作从认证会话读取 CSRF Token，并通过统一函数生成请求头。
- 无数据成功结果使用 `null`，不得依赖 204、空字符串或未定义值表达成功。
- 文件下载统一走文件 Service；文件名、媒体类型和内容的还原逻辑不得散落在页面中。
- 不记录或展示 Token、Cookie、密码、完整文件内容、堆栈和服务端内部异常。

### 5.3 TanStack Query

- Query Key 只能通过 `data-provider/query-keys.ts` 创建，查询和失效不得临时手写数组。
- 所有会改变结果的参数都必须进入 Query Key；对象参数应保持字段稳定且可序列化。
- 每个 Query 明确 `enabled`、`staleTime`、重试和刷新策略；使用全局默认值时无需重复声明。
- 能取消的请求应把 Query 提供的 `signal` 传到 HTTP Client，避免页面离开后继续无效工作。
- Mutation 成功后只失效或更新受影响的缓存；禁止清空整个 Query Cache。
- 同一业务动作的多个缓存失效封装成命名函数，并全部使用 `queryKeys` 工厂。
- 页面要区分首次加载 `isPending`、后台刷新 `isFetching`、失败 `isError` 和空数据，不用单一 Loading 覆盖全部状态。
- 全局 Query/Mutation 错误由 Provider 统一提示；页面只处理需要局部恢复、特殊文案或字段定位的错误，避免重复 Toast。
- 可安全回滚时才做乐观更新，并完整实现取消请求、保存旧值、失败回滚和最终同步。

## 6. 客户端状态

按以下顺序选择状态位置：

1. 能从 Props、Query 或现有 State 推导：直接计算；
2. 仅当前组件或组件树使用：`useState`、`useReducer` 或 Context；
3. 需要分享、刷新保留或支持前进后退：URL；
4. 来自服务端：TanStack Query；
5. 跨页面共享的纯客户端状态：Zustand。

- Zustand 不得保存 Query 已管理的接口数据，不得充当服务端缓存。
- Store 按单一业务职责拆分，State 与 Action 共同定义；Action 使用动词并封装状态变更。
- 组件使用 selector 订阅所需的最小切片，禁止无条件订阅整个 Store。
- 弹窗开关、表单输入、临时选择和 Hover 等状态保留在组件本地。
- 持久化 Store 必须声明版本和迁移策略，不得持久化 Token、密码或其他敏感数据。
- Context 用于稳定的依赖和 Provider 组合，不用来替代高频更新的 Store。

## 7. TypeScript、命名与格式

### 7.1 类型规则

- 保持项目 `strict`、`exactOptionalPropertyTypes` 和 `noUncheckedIndexedAccess` 开启。
- 禁止 `any`、`@ts-ignore` 和无依据的非空断言。必要的不安全转换必须限制在单个边界适配函数中，并先做运行时校验。
- 优先使用类型推导；公共函数、组件 Props、Service 输入输出和复杂返回值应显式表达类型。
- 纯类型导入使用 `import type`。优先使用可辨识联合表达有限状态，避免多个可能互相矛盾的布尔字段。
- API DTO、页面 View Model 和表单输入模型按职责区分，不直接修改 Query Cache 中的对象。
- 金额使用整数分；日期使用 `YYYY-MM-DD`；时间点使用 ISO 8601。格式化只在展示边界完成。

### 7.2 命名规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 组件、类型、接口 | `PascalCase` | `DeleteRecordButton`、`UiState` |
| 函数、变量、Hook | `camelCase` | `formatLocalMinute`、`useOverview` |
| 组件文件 | `PascalCase.tsx` | `AccessibleAnnouncer.tsx` |
| Hook、Service、Store | 项目现有的小写命名 | `use-login.ts`、`finance.service.ts`、`ui.store.ts` |
| 布尔值 | 谓词前缀 | `isPending`、`hasPermission`、`canRestore` |
| 事件 Props / 处理函数 | `onXxx` / `handleXxx` | `onClose`、`handleSubmit` |
| 集合 | 复数名词 | `recentEntries`、`queryKeys` |
| 常量 | 语义明确；模块级不强制全大写 | `routeFallback`、`MAX_LINES` |

- 禁止 `data2`、`obj`、`temp`、`handleData`、`manager`、`helper`、`utils` 等无法表达职责的命名。
- 同一概念使用同一个词，不混用 `fetch`、`get`、`load` 表示相同操作。
- 函数使用动词开头并只做一件事；参数超过三个时优先使用参数对象。

### 7.3 格式与注释

- 格式统一交给 Biome：2 空格缩进、双引号、分号、尾随逗号、100 字符行宽。
- Import 按工具规则排序，不手工制造特殊分组；删除未使用的 Import 和死代码。
- 注释解释设计原因、浏览器限制或业务不变量，不复述代码行为。
- 禁止保留注释掉的旧代码、文件内变更日志和无负责人、无上下文的 TODO。
- 单个 Web 源文件不得超过 600 行；接近上限时应按职责提前拆分，而不是压缩格式规避门禁。

## 8. 样式与组件库

- 优先使用 `animal-island-ui` 现有组件及其语义属性，不重复实现 Button、Modal、表单控件等基础能力。
- Tailwind 用于页面布局和局部样式；全局样式、主题变量和跨页面规则放在 `styles/`。
- 颜色、字号、圆角、阴影和间距优先使用现有设计 Token 或稳定的 Tailwind 尺度。
- 避免散落魔法颜色、任意像素值和大段重复类名。重复且有业务含义的样式应提取为组件，不创建无语义的类名仓库。
- 不使用 `!important` 掩盖层级问题，不用过深选择器依赖第三方组件内部 DOM。
- 自定义动画必须尊重 `prefers-reduced-motion`；避免影响布局的高成本动画。
- 装饰图片使用空 `alt` 并隐藏于辅助技术；有内容含义的图片提供简洁准确的替代文本。
- 为图片声明宽高，按实际显示尺寸提供资源，避免布局偏移和无谓下载。

## 9. 交互、错误与无障碍

- 优先使用 `button`、`a`、`input`、`label`、`nav`、`main` 等原生语义元素，不用可点击 `div` 模拟控件。
- 每个交互控件必须有可访问名称，并支持键盘操作和清晰的焦点样式。
- 弹窗和抽屉打开后管理焦点，Escape 可关闭时必须恢复触发点焦点；提交中应阻止重复操作。
- 加载、禁用、空数据、失败、提交中和成功反馈必须有明确且不互相矛盾的 UI。
- 状态变化通过统一通知系统和 `AccessibleAnnouncer` 同步给视觉用户与辅助技术；紧急错误使用 `alert`，普通状态使用 `status`。
- 错误文案说明发生了什么以及用户下一步能做什么，不暴露内部异常，也不只显示“出错了”。
- 表单字段必须有可见标签；校验错误关联到对应字段，提交失败后焦点移动到首个可修复位置。
- 响应式行为至少覆盖桌面和项目配置中的移动端视口；不得只通过隐藏功能解决小屏问题。

## 10. 性能

- 路由页面默认懒加载，首屏必需页面和框架组件才可同步导入。
- 避免在渲染期间执行昂贵排序、深拷贝或重复格式化；确认存在成本后再缓存。
- 大列表优先分页或虚拟化，不一次渲染无边界数据。
- Query Key 和缓存范围应与页面需求一致，避免重复请求和过度失效。
- 不在全局 Store、Context 或顶层组件中存放高频、局部变化的状态。
- 引入新依赖前先确认现有平台、组件库或工具无法满足需求，并评估包体积、维护状态和浏览器兼容性；新增依赖需要明确授权。

## 11. 测试规范

### 11.1 单元与组件测试

- 纯函数、Store、Query 配置和错误转换使用 Vitest；组件交互使用 Testing Library 和 `userEvent`。
- 测试从用户可观察行为出发，优先按 Role、Label 和可见文案查询，不依赖组件内部 State、类名或 DOM 层级。
- 一个测试只描述一个行为场景，名称使用清晰中文说明“条件 + 结果”。
- 测试按 Arrange、Act、Assert 组织；公共准备逻辑提取为有业务含义的构建器或渲染函数。
- 不滥用快照。视觉结构、类名堆栈和第三方组件内部实现不应成为脆弱断言。
- 时间、网络、随机值和浏览器 API 必须固定或替换；测试不得依赖执行顺序和开发机已有状态。
- 修改行为至少覆盖正常、空数据、失败和关键交互；修复缺陷必须增加能先复现问题的回归测试。

### 11.2 端到端测试

- Playwright 覆盖登录、导航、关键写操作、错误恢复和跨页面主流程，不重复穷举组件级细节。
- 接口响应使用与共享契约一致的模拟数据，明确覆盖认证失败、空数据和服务异常。
- 关键流程同时验证桌面和移动端；无障碍交互至少验证可访问名称、键盘操作和焦点恢复。
- 定位器优先使用 Role、Label 和用户可见文本，禁止依赖易变 CSS 类。
- 测试失败应保留可诊断的 Trace；不得用任意等待时间掩盖竞态。

## 12. 交付门禁

前端改动提交前至少运行：

```bash
bun run lint
bun run check:web-size
bun run --cwd apps/web typecheck
bun run test:web
bun run --cwd apps/web build
```

涉及路由、登录、响应式导航、关键表单或跨页面流程时，额外运行：

```bash
bun run test:e2e
```

- 不得沿用旧的“全部通过”结论；必须报告本次实际执行的命令和结果。
- 检查失败时，记录失败项、原因和影响范围，不得删除测试、放宽类型或禁用规则绕过。
- 文档、纯样式等低风险改动可以按影响范围缩减测试，但至少执行格式检查，并说明未运行项。

## 13. Code Review 清单

- 组件、Hook、Service 和 Store 是否各自只有一个清晰职责？
- 是否保持 `页面 → data-provider → service → http-client/shared` 的单向依赖？
- 页面是否直接请求接口，Service 是否反向依赖 React，公共组件是否混入业务？
- 状态是否放在正确位置，是否重复保存 Query 数据或可派生数据？
- Query Key 是否统一生成，参数是否完整，Mutation 是否只失效受影响缓存？
- 是否存在不必要的 Effect、Memo、Callback、Context 或过早抽象？
- 加载、刷新、空数据、错误和提交状态是否清晰？
- 类型边界是否经过验证，是否存在 `any`、强转、非空断言或敏感信息泄露？
- 路由页面是否按约定懒加载并提供占位、鉴权和错误兜底？
- 交互是否具备语义标签、键盘操作、焦点反馈和屏幕阅读器通知？
- 样式是否复用组件库与设计 Token，并兼顾移动端和减少动画偏好？
